# QuickNode Streams server-side filter — design (Stream Latency task 3)

## Problem

The `Block with Receipts` dataset QuickNode pushes to `/base-live` carries **every**
transaction + receipt in the block (commonly 600 KB-1.3 MB, 100-300+ transactions),
regardless of how many monitored wallets Decoda actually watches. Today that is one
wallet. Decoda receives, HMAC-verifies, decodes, and normalizes all of it, then
discards everything except the one matching transaction. See
`quicknode_stream_latency_profile` (measured, in-process): decode + normalize +
match for a realistic 280-tx/~800KB block costs single-digit milliseconds even fully
unfiltered, so this is **not** the dominant cause of the observed lag (see the Stream
Latency root-cause report) — but it is real, unnecessary bandwidth and Decoda-side
CPU that scales with chain activity and with every additional monitored wallet, and
QuickNode Streams supports removing it server-side.

## Options evaluated

| Option | How it works | Pros | Cons |
|---|---|---|---|
| **A. Filter function with an address allowlist** (recommended for the pilot) | A JS filter function deployed on the Stream checks `tx.from`/`tx.to` (and, optionally, log `address`/topics) against a list of addresses and returns `null` to drop non-matching entries, or the (optionally trimmed) block otherwise. | Simplest to reason about and deploy; keeps full evidence fields for a match; QuickNode runs it, so non-matching blocks never reach Decoda's network path at all. | The address list is baked into the deployed filter's closure at the time it's set — updating it means redeploying the filter (see propagation below). |
| B. QuickNode Key-Value Store | The filter function reads a QuickNode-managed KV Store (updated via QuickNode's API) instead of a literal in the filter body, so the address list can change without redeploying the filter code. | Decouples "which addresses" from "the filter logic"; better fit once multiple workspaces each add/remove wallets often. | Extra moving part (a second system holding truth about monitored addresses) and an extra QuickNode API integration Decoda would need to own and keep in sync; not justified for a single-wallet pilot. |
| C. Generated filter configuration | A script (this task) reads Decoda's own `targets` table and emits ready-to-paste filter source, so the *address list* is never hand-typed or hardcoded in application source, even though option A's deployed filter still embeds it literally until the next regeneration. | No new moving parts beyond option A; addresses always come from the same canonical query the webhook itself uses (`_BASE_WALLET_TARGETS_SQL`), so the filter can never drift from what Decoda actually matches. | Same redeploy-to-update characteristic as option A. |
| D. Separate native-transfer vs. contract-log paths | Two Streams/filters: a cheap one for plain ETH transfers (`tx.to`/`tx.from` only, no receipt needed) and a second for contract/log-based detection (ERC-20 `Transfer`, etc.), each with its own dataset/filter shape. | Lets a future native-only monitor skip requesting receipts entirely (smaller payload). | Real complexity increase (two Streams, two webhook contracts, two checkpoints) for zero pilot benefit — today's monitored asset needs both native transfers and receipt status. Not justified until there is a concrete contract-log detector that does not also need native-transfer coverage. |

**Recommendation for the current pilot/demo: A + C together.** A single filter
function with a literal address allowlist, where that literal list is produced by a
script reading Decoda's own database — never typed by hand, never hardcoded in
application source. Option B (KV Store) is the natural next step once multiple
workspaces are actively adding/removing Base wallets often enough that a manual
filter redeploy per change is impractical; it is not needed for one pilot wallet and
would add an integration surface with nothing yet to justify it. Option D is deferred
until a real contract-log-only detector exists.

## Why "do not hardcode one demo wallet into application source" is satisfied

The filter's address list is **generated from `targets`** (the same
workspace-scoped, `target_type='wallet'` / `chain_network` Base rows the webhook
itself loads — see `_BASE_WALLET_TARGETS_SQL` in `quicknode_streams.py`), by
`services/api/scripts/generate_quicknode_stream_filter.py`. Nothing in
`services/api/app/**` ever names a specific wallet. Adding a second monitored Base
wallet requires zero application code changes — only re-running the generator and
re-pasting its output into the QuickNode dashboard (or, once justified, pushing it to
a KV Store instead).

## The filter (option A)

```javascript
// QuickNode Streams filter function — Base "Block with Receipts" dataset.
// Generated by services/api/scripts/generate_quicknode_stream_filter.py — do not
// hand-edit MONITORED_ADDRESSES; regenerate it instead so it always matches what
// Decoda's own targets table resolves.
function main(stream) {
  const MONITORED_ADDRESSES = new Set([
    // <<GENERATED_ADDRESS_LIST>> — lowercase 0x addresses, one per active Base
    // wallet target. Placeholder only: never commit a real address list into this
    // repo's docs; the generator writes the live list to a local, gitignored file.
  ]);

  const data = stream.data ? stream.data[0] : stream[0];
  if (!data || !data.block || !Array.isArray(data.block.transactions)) return null;

  const matchedHashes = new Set();
  const matchedTxs = data.block.transactions.filter((tx) => {
    const from = (tx.from || '').toLowerCase();
    const to = (tx.to || '').toLowerCase();
    const hit = MONITORED_ADDRESSES.has(from) || MONITORED_ADDRESSES.has(to);
    if (hit) matchedHashes.add((tx.hash || '').toLowerCase());
    return hit;
  });

  // No monitored address anywhere in this block: drop it. QuickNode still bills
  // the block as processed (see "Billing" below) but sends Decoda nothing —
  // this is the bandwidth/CPU saving, not a credits saving.
  if (matchedTxs.length === 0) return null;

  // Keep every evidence field the webhook needs (tx hash, block number, from, to,
  // value, timestamp, receipt status/logs for the matched tx) — never trim a
  // matched transaction's own fields. Receipts are filtered to the SAME matched
  // hashes so a real transfer's status/logs are never silently dropped.
  const matchedReceipts = Array.isArray(data.receipts)
    ? data.receipts.filter((r) => matchedHashes.has((r.transactionHash || '').toLowerCase()))
    : [];

  return {
    block: {
      number: data.block.number,
      timestamp: data.block.timestamp,
      transactions: matchedTxs,
    },
    receipts: matchedReceipts,
  };
}
```

This preserves the exact shape `_extract_tx_dicts` already parses (`block.transactions`
+ top-level `receipts`, matched by `transactionHash`), so **no Decoda application code
changes are required** to consume a filtered stream — `normalize_base_stream_tx` reads
the same fields either way. A block containing no monitored-address transaction never
reaches Decoda at all; a block that does contain one arrives with every field the
webhook currently uses, plus the full receipt (status + logs) for that transaction
specifically, so evidence quality for a match is unchanged — only the ~99%+ of
irrelevant transactions in the same block are removed before the payload leaves
QuickNode.

## Evidence completeness (test requirement: "Stream filtering cannot remove required evidence")

For every transaction the filter passes through, Decoda still receives, unreduced:
tx hash, block number, from, to, value, timestamp (block-level), receipt status, and
that transaction's own logs. The filter only ever removes whole transactions that
matched **no** monitored address — it never trims fields off a transaction it keeps.
`services/api/tests/test_quicknode_stream_filter_generator.py` (added by this task) asserts this contract
by rendering the real filter template and executing the actual generated JavaScript
via Node.js (not a Python re-implementation that could drift from what QuickNode
would really run), so a future filter edit that started dropping a required field
would fail CI rather than silently ship.

## Propagation of address changes

The deployed filter's `MONITORED_ADDRESSES` is a literal snapshot at generation time.
Re-run the generator and update the Stream's filter in the QuickNode dashboard (or
push a new KV Store value, once on option B) whenever a Base wallet target is
added, edited, or removed. Until that redeploy, a **newly added** wallet's transfers
will not reach `/base-live` via the filtered stream — but they remain fully covered
by Stable RPC Polling (the always-on 900s fallback, unaffected by any of this) and by
the QuickNode live RPC worker, so detection correctness never depends on the filter
being current — only realtime latency for a *just-added* wallet briefly does, until
the next regeneration. This is a materially different, and looser, guarantee than the
in-process target cache added in this same task (task 2), which bounds propagation to
a fixed ~10s TTL automatically; the filter has no such automatic bound today. Document
this explicitly to operators and re-run the generator as a standard step of "add a new
Base wallet target" until/unless option B (KV Store) removes the manual step.

## Billing — filtering does not reduce QuickNode credits

**QuickNode Streams billing is based on blocks processed, not bytes delivered to the
destination.** A server-side filter reduces the payload Decoda receives and parses
(bandwidth, HMAC-over-bytes cost, JSON decode cost, normalization cost — all
measured negligible in this task's profiling, but real and worth removing) but the
Stream still processes (and is billed for) every Base block whether or not the filter
ultimately returns `null` for it. Do not present this filter as a cost-reduction
measure; it is a Decoda-side bandwidth/CPU reduction and, more importantly, a step
toward the multi-workspace design below.

## Multi-workspace path (not implemented in this pilot)

The generator already reads every active Base wallet target across every workspace
(the same intentionally-unscoped query the webhook uses — a single shared Stream
serves every workspace's Base wallets, matched the same way stable RPC polling does).
Nothing about the filter or generator is single-tenant. The remaining work for a
larger multi-workspace deployment is operational, not architectural: moving from
"regenerate and paste" (option A+C) to "push to a KV Store on every target
create/update/delete" (option B), so address propagation no longer requires a human
redeploy step. That is a deliberate follow-up, not part of this pilot's smallest safe
change.
